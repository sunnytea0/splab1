# Базова лінія для ЛР4

## Збірка
git-хеш: **553e22a** (банер `FW version=`). Вимірювання S1–S3 зняті на 1853345; різниця лише в `scen_finish`, який повертає задачі до стандартних періодів після сценарію.
Збірка: `docker run --rm -v "${PWD}:/workspace" -w /workspace stm32-build make all`, запуск у Wokwi (Форма B).

## Сценарії (однаково в ЛР4)
| Сценарій | Як відтворити | Тривалість |
|---|---|---|
| S1 | UART: `SCEN 1 30` | 30 с |
| S2 | `SCEN 2 30` (STATS кожні 5 с імітує потік команд) | 30 с |
| S3 | `SCEN 3 30` + 30–50 натискань кнопки + потік байтів у UART | 30 с |
| 6.2 | `BUSY <мс>`, від'єднання SDA, тривалий прогін S2 ≥ 1 год | див. звіт |

Автозапуск без введення: збірка з `-DAUTORUN_SCEN` (S1→S2→S3, по 30 с).
Перед кожним сценарієм перевіряй у рядку `SCEN_START` значення `seconds=`.

## Інструментарій
Команди: STATS RESET HIST MEM VER SELFTEST IMU REPORT LONG BUSY SCEN HELP. Формат рядків: STAT / JIT / LAT / LOAD / RX / MEM / HIST.
Аналіз: `python tools/analyze_stats.py docs/metrics/S1.log docs/metrics/S2.log docs/metrics/S3.log`.
Аналізатор: Wokwi logic analyzer, канали BTN, IMU, LONG, BTNRX (піни PB0, PA6, PA7, PA8); запис VCD при зупинці симуляції.

## Таблиця метрик
Повна таблиця: `docs/metrics/results.md`. Ключові числа для порівняння в ЛР4 (S3, 30 с): IMU late max 116,7 мс, missed 629; кнопка max 99,2 мс (n = 153); CPU load max 46 %; stack 584/1024 Б; heap 1468 Б; flash 26 236 Б (80,07 %), RAM 3048 Б (24,8 %).

## Гіпотези з реєстру обмежень
1. З витісненням і пріоритетами реакція на кнопку під longop знизиться з ≈ 99 мс до < 1 мс (час перемикання контексту).
2. IMU late max у S3 впаде з ≈ 117 мс до менш ніж одного такту планувальника; missed → 0 за умови вищого пріоритету IMU.
3. CPU load не зросте суттєво (S3 ≈ 46 %), але додасться RAM на стеки задач: flash вже 80 %, тому ОС має вміститися в ≈ 6 КБ flash.
4. Друк STATS (≈ 104 мс) не повинен блокувати IMU, якщо вивід винести в окрему задачу з нижчим пріоритетом.
