# Реєстр обмежень super loop

> Усі числа виміряні (docs/metrics/results.md). Таймінги Wokwi симульовані.
> Обмеження 4 і 5 мають часткові докази: потрібні сценарії 6.2 п. 3 і п. 4.

### Обмеження 1: Затримка реакції на подію залежить від найдовшої задачі (час реакції)
- **Симптом:** FR-07 (реакція на кнопку ≤ 50 мс) порушується в S3, коли кнопку натиснуто під час довгої операції.
- **Доказ:** LAT:btn max = 99 199 мкс (S3, n = 153) проти ≈ 100 мкс без longop (після SCEN_DONE: 51 і 93 мкс). Логічний аналізатор: ≈ 99,2 мс; натискання під LONG — 51,7 і 65,0 мс. У шести прогонах S3 max стабільно 91–109 мс.
- **Причина в архітектурі:** Подія обробляється лише коли цикл доходить до перевірки кнопки. Найгірша затримка = сума часів усіх задач одного проходу ≈ t_imu + t_adc + t_report + t_longop ≈ 115,6 мс; це властивість кооперативного циклу, а не помилка коду.
- **Як обійти без ОС:** Розбити longop на кроки ≤ 1 мс (машина станів) або виконувати реакцію в ISR. Ціна: складніший код, збереження стану між кроками, ISR не може друкувати і блокувати.
- **Що могла б дати ОС:** Витіснення і пріоритети: задача кнопки (високий пріоритет) переривається планувальником longop (низький пріоритет).
- **Чого коштуватиме ОС:** RAM на стеки задач (flash вже 80 %), накладні перемикання контексту, інверсія пріоритетів, гонки даних, переповнення стека задачі.
- **Гіпотеза для ЛР4:** Max затримки кнопки в S3 знизиться з ≈ 99 мс до < 1 мс (кілька тіків планувальника).

### Обмеження 2: Джитер і пропуски періодичної задачі IMU (джитер)
- **Симптом:** FR-03 / FR-05: IMU втрачає виміри та запізнюється.
- **Доказ:** S3: JIT:imu late_max = 116 729 мкс, missed = 629, виконано 2335 із ≈ 3000; S1: 47 мкс, 0 пропусків (різниця S3 − S1 ≈ 116,7 мс). S2: один лише блокувальний друк STATS (≈ 104 мс) дав late_max 99,3 мс і 53 пропуски. Стабільно в шести прогонах (late_max 113,8–119,6 мс).
- **Причина в архітектурі:** IMU запускається лише коли цикл дійде до нього; поки виконується longop (100 мс) або printf (13,7 мс), запуск відкладається. Пропущені періоди = час блокування / період.
- **Як обійти без ОС:** Виносити термінове в таймерне переривання з DMA; розбивати longop і друк на кроки. Ціна: складність, спільні дані (volatile, критичні секції).
- **Що могла б дати ОС:** Пріоритетний планувальник: IMU з вищим пріоритетом витісняє longop і друк; програмні таймери.
- **Чого коштуватиме ОС:** Нові класи помилок (взаємне блокування, інверсія пріоритетів), RAM під стеки, перемикання контексту.
- **Гіпотеза для ЛР4:** late_max IMU у S3 з ≈ 117 мс до менш ніж одного такту планувальника; missed 629 → 0.

### Обмеження 3: Блокувальний вивід в UART (довгі операції)
- **Симптом:** Блок STATS і рядок звіту зупиняють усі інші задачі; впливає на FR-08/FR-09 і на всі періодичні задачі.
- **Доказ:** STAT:report avg = 13 753 мкс (max 14 919); блок STATS блокує цикл на ≈ 104 мс (STAT:loop max 104 329 мкс у S2). Розрахунок: ≈ 123 Б × 10 біт / 115200 ≈ 10,7 мс; виміряне на ≈ 28 % більше (гіпотеза: форматування printf без апаратного ділення на Cortex-M0+ та модель UART у Wokwi).
- **Причина в архітектурі:** HAL_UART_Transmit блокувальний і виконується в тому ж потоці, що й усі задачі; у super loop немає іншого місця, де можна «почекати».
- **Як обійти без ОС:** Передача через DMA або ISR з кільцевим буфером; друкувати великі блоки частинами. Ціна: буфер ≈ сотні байт RAM, обробка переповнення буфера.
- **Що могла б дати ОС:** Окрема задача виводу з чергою і низьким пріоритетом; блокування з timeout.
- **Чого коштуватиме ОС:** RAM під черги/буфери, синхронізація, втрата повідомлень при переповненні черги.
- **Гіпотеза для ЛР4:** Друк STATS не викликатиме пропусків IMU (S2: missed 53 → 0).

### Обмеження 4: Втрата байтів UART RX при опитуванні (спільні ресурси / команди)
- **Симптом:** Команди з терміналу приходять спотвореними, коли цикл зайнятий («SSCEBSCEN», «30030» замість «30»).
- **Доказ:** Спостерігалось вручну («seconds=30030»: сценарій завершився одразу з нульовою статистикою). Лічильник RX overruns = 0 в усіх прогонах, але команди вводились повільно; окремий тест потоку байтів під час longop (сценарій 6.2 п. 3) ще не виконано.
- **Причина в архітектурі:** Приймач без апаратного FIFO зберігає один байт; опитування раз на прохід (≈ 115 мс у S3) не встигає за швидким вводом.
- **Як обійти без ОС:** Приймання через ISR + кільцевий буфер (можна без ОС). Ціна: спільні дані між ISR і циклом, volatile, критичні секції.
- **Що могла б дати ОС:** Черга повідомлень між ISR і задачею команд.
- **Чого коштуватиме ОС:** RAM під чергу, нові класи помилок (гонки, взаємне блокування).
- **Гіпотеза для ЛР4:** Втрат байтів на швидкому потоці не буде (RX overruns = 0 при потоці без пауз); час відповіді на команду ≈ 1 такт планувальника.

### Обмеження 5: Відмова сенсора блокує весь цикл (обробка відмов)
- **Симптом:** FR-10: при зникненні MPU6050 читання по I²C блокувальне, тож затримуються всі інші задачі.
- **Доказ:** Структурна властивість драйвера (HAL_I2C_Mem_Read з timeout); час блокування і поведінка інших задач потребують виміру сценарієм 6.2 п. 4 (від'єднання SDA) — ще не виконано.
- **Причина в архітектурі:** Один потік виконання: поки чекає timeout однієї задачі, інші не виконуються.
- **Як обійти без ОС:** Короткий timeout, лічильник помилок і відкладений повтор (машина станів), I²C через DMA/переривання. Ціна: складність, нові стани.
- **Що могла б дати ОС:** Блокування з timeout у задачі IMU без впливу на інші; watchdog на задачу.
- **Чого коштуватиме ОС:** RAM, перемикання контексту, потреба в аналізі пріоритетів.
- **Гіпотеза для ЛР4:** Час блокування інших задач при відмові сенсора впаде з довжини timeout до ≈ 0.

### Обмеження 6: Додавання задачі вимагає змін у багатьох місцях (модульність і складність)
- **Симптом:** Кожна нова задача розмножується по файлу app.c.
- **Доказ:** Для нової задачі змінюються 5 місць: оголошення ptask_t, App_Init (ptask_init), App_Run (виклик у циклі), stats_reset_all, print_stats. Стан розкиданий по глобальних змінних; порядок задач у циклі — неявний пріоритет.
- **Причина в архітектурі:** У super loop планування вшите в код головного циклу; немає реєстру задач.
- **Як обійти без ОС:** Таблиця задач (структури + покажчики на функції) і універсальний диспетчер. Ціна: трохи RAM/flash, власний «міні-планувальник».
- **Що могла б дати ОС:** Створення задачі одним викликом API, окремий стек і пріоритет.
- **Чого коштуватиме ОС:** Кожна задача — власний стек (RAM), налаштування пріоритетів, ризик переповнення стека.
- **Гіпотеза для ЛР4:** Додавання задачі: змін у коді 5 → 1 місце (створення задачі).

### Обмеження 7: Запас пам'яті під розширення (пам'ять)
- **Симптом:** Після додавання вимірювального коду flash заповнений на 80 %.
- **Доказ:** --print-memory-usage: FLASH 26 236 Б із 32 КБ (80,07 %), RAM 3048 Б (24,8 %); стек (stack painting) 584–616 Б із 1024 Б; heap 1468 Б. Найбільші символи: __sfvwrite_r 756 Б, _vfprintf_r 700 Б, _printf_i 648 Б (≈ 2,1 КБ форматованого виводу), програмне ділення __divsi3 460 Б.
- **Причина в архітектурі:** Малий кристал (32 КБ flash) і код форматування (printf) та HAL забирають основну частину flash.
- **Як обійти без ОС:** Прибрати printf з плаваючою комою, вимкнути невикористаний HAL, зберігати строки в flash. Ціна: гірша діагностика.
- **Що могла б дати ОС:** ОС додає код ядра і RAM на стеки; керуватиме пам'яттю по задачах.
- **Чого коштуватиме ОС:** Ядро та стеки задач можуть не вміститись у ≈ 6,5 КБ вільного flash; вимагає перевірки в ЛР4.
- **Гіпотеза для ЛР4:** Збірка на RTOS займе ≥ 6 КБ flash і додаткові КБ RAM під стеки; запас flash може вичерпатись.

## Що super loop робить краще за ОС
Детермінізм без перемикань контексту, мінімум RAM (стек 576–616 Б, heap 1468 Б), простота налагодження, швидкий старт.
